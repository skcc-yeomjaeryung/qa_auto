# 14_13 — 단일 Agentic Core·모델 결정론·Agent 모니터링

- 날짜: 2026-08-06
- Phase: 14.배치테스트
- 회차: 13
- 작업자/Agent: Codex
- 기준: D-012 SDD Runtime을 D-016 단일 Agentic Core로 책임 재편

## 1. 결론

`corev2`를 추가하지 않고 기존 `backend/app/core/` 하나를 책임별 package로 재편했다. 분석·매핑·그래프·시나리오·입력 추천·실행 Workflow는 기존 `PlatformRunnerAdapter`를 유지한 채 새 `AgentRuntime`과 같은 LangGraph 실행 경로를 사용한다. 이 회차 당시 남겼던 re-export wrapper는 다음 회차 14_14에서 영향도 검증 후 완전 제거됐다.

프로젝트 관리자는 원시 모델 이름을 고르는 대신 AI 실행 정책만 선택한다. Planner는 Workflow capability → 허용 Agent → Skill/Tool → 모델 요구사항 순으로 Plan을 만들고, ModelSelector는 하드 필터와 정책별 가중 점수로 모델을 결정한다. 선택 모델은 Trace에만 표시되는 값이 아니라 Tool subprocess 환경에 실제 주입된다.

Manage 메뉴에는 `모델 관리`와 `Agent 모니터링`을 추가했다. Agent 모니터링은 비공개 사고과정이 아닌 후보 점수, 제외 이유, 선택 결과, Plan, 실행 상태, Artifact, Review, Reduce를 보여준다.

## 2. 변경 전과 변경 후

| 관점 | 변경 전 | 변경 후 |
|---|---|---|
| Core 구조 | planner/orchestrator/reviewer/reducer가 평면 경로에 집중 | runtime/planning/execution/quality/models/context/prompts/observability/catalog 책임 분리 |
| 기존 서비스 | 각 서비스가 `PlatformRunnerAdapter` 사용 | Adapter 계약을 유지하고 내부만 `AgentRuntime`으로 전환 |
| Plan | capability → 첫 Skill/Tool | capability → Named Agent 허용 검증 → Skill priority → 모델 요구사항 → `plan/v2` |
| 모델 | 환경설정의 단일 LLM | SQLite model profile + `/v1/models` health + 프로젝트 AI policy |
| 모델 선택 | 호출부가 사실상 고정 | 하드 필터 후 품질·신뢰도·속도·비용 정책 점수, tie-break 결정 |
| Context | 매 단계 전체 입력 복제 | 큰 입력을 한 번 저장하고 `contextRef` 전달, 선행 결과 중 필요한 값만 merge |
| Prompt | 일부 서비스가 파일을 직접 읽음 | 역할 Prompt를 `app/prompts/`에 두고 LangChain `PromptCatalog`로 로드 |
| 관측 | 최종 성공/오류 중심 | Workflow·Plan·모델 후보·Skill/Tool·Review·Reduce 이벤트의 Trace |
| 보안 | 모델 연결 secret 경계 불명확 | API key SQLite/응답/Trace 미저장, 민감 key 마스킹 |

## 3. 단일 Core 책임 구조

```text
Console / API / Service
  → PlatformRunnerAdapter (기존 호환 경계)
  → AgentRuntime (안정된 Core facade)
  → LangGraph
      route
      → plan
          Workflow Registry
          → Agent Registry 허용 범위
          → Skill Registry / Capability
          → ModelSelector
      → execute
          Context restore
          → dependsOn 결과 merge
          → ToolRuntime / Skill script / worker
      → review
          Schema·Evidence 계약 확인
      → reduce
          Artifact 중심 다음 Context 축약
      → response
  → Agent Trace
```

### Core package

| 경로 | 책임 |
|---|---|
| `core/runtime` | 모든 agentic 서비스의 공통 facade |
| `core/planning` | Plan v2, Agent·Skill·Tool·모델 결정 |
| `core/execution` | dependency 순서와 단계 출력 전달 |
| `core/quality` | Reviewer와 Reducer |
| `core/models` | 등록·health·정책·선택 |
| `core/context` | 대량 입력 reference store |
| `core/prompts` | LangChain prompt loader·version·hash |
| `core/observability` | SQLite bounded Trace·민감정보 제거 |
| `core/catalog` | Named Agent와 허용 Skill 경계 |

이 회차 당시 구 경로는 compatibility wrapper였으며 실제 중복 클래스는 없었다. 2026-08-07 14_14에서 구 package·import·생성 캐시를 제거하고 `planning`, `execution`, `quality`만 공식 경로로 확정했다.

## 4. 모델 결정론

### 4.1 등록 정보

- 표시명, provider, endpoint, API base path, `/v1/models` path, 실제 model ID
- 내부/외부 배포 위치
- chat/code/vision/embedding capability
- context window, structured output, tool calling 지원
- 품질·비용·속도·신뢰도 점수
- enabled, health, latency, 발견된 모델 목록
- API key는 요청에서만 받아 프로세스 메모리에 유지하며 SQLite나 응답에는 저장하지 않는다.

### 4.2 선택 순서

1. Skill frontmatter의 모델 요구사항을 읽는다.
2. disabled, capability 부족, context 부족, structured/tool 미지원, health down 후보를 제외한다.
3. `internal_only`는 외부 배포 후보를 추가로 강제 제외한다.
4. 남은 후보를 정책별 가중치로 계산한다.
5. health unknown/degraded penalty와 scenario/evidence 품질 bonus를 적용한다.
6. 점수 내림차순, profile ID 오름차순으로 결정해 같은 입력은 같은 결과를 만든다.
7. 적합 후보가 없고 Skill이 허용한 경우에만 `deterministic_fallback`으로 전환한다.

| 정책 | 품질 | 신뢰도 | 속도 | 비용 |
|---|---:|---:|---:|---:|
| 자동 추천 | 35% | 30% | 20% | 15% |
| 비용 절약 | 15% | 20% | 20% | 45% |
| 균형 | 30% | 30% | 20% | 20% |
| 최고 품질 | 55% | 30% | 10% | 5% |
| 내부망 전용 | 35% | 35% | 20% | 10% |

### 4.3 실제 검증 Trace

`balanced` 시나리오 Plan에서 기본 로컬 `llama3.2`는 기본 가중 점수 80점에 health unknown -5점, 품질 민감 작업 bonus 3.75점이 적용돼 78.75점으로 선택됐다. 임베딩 모델은 `chat`, `code`, 최소 context 16384, structured output 요구사항을 충족하지 못해 후보에서 제외됐다. 이 계산과 제외 사유가 Trace `PLAN-145e24b007bc`에 표시됐다.

선택 결과는 ToolRuntime이 subprocess의 다음 환경으로 주입한다.

- `LLM_BASE_URL`
- `LLM_MODEL`
- `LLM_API_KEY`
- `LLM_ENABLED`

따라서 ModelSelector는 설명용 화면이 아니라 실제 Skill 실행 모델을 결정한다.

## 5. Prompt 관리

역할 시스템 프롬프트를 `backend/app/prompts/`에 배치하고 `PromptCatalog`가 LangChain `ChatPromptTemplate`로 렌더링한다. 각 Prompt는 version과 SHA-256을 가진다.

| 역할 | Prompt |
|---|---|
| 모델 후보 비교 계약 | `agent_roles/model_advisor_system.md` |
| Evidence Reviewer | `agent_roles/evidence_reviewer_system.md` |
| Context Reducer | `agent_roles/context_reducer_system.md` |
| Scenario 생성/분류/중복 제거 | `scenario/*.md` |
| 실행 입력 바인딩/판정/요약 | `run/*.md` |
| 설계 문서 VLM 분석 | `project_context/vlm_ocr_system.md` |

VLM 프로젝트 문서 분석에 남아 있던 직접 `read_text` 호출도 PromptCatalog 경로로 통합했다. 모델 결정의 하드 필터는 Prompt에 위임하지 않고 코드가 강제한다. Prompt는 허용된 후보의 역할·설명 계약이며 근거 없는 모델/Skill/Tool을 발명할 수 없다.

## 6. Agent 모니터링

`/manage/agents`와 `/api/agent-monitor/*`는 아래 사건을 Trace 단위로 제공한다.

- Workflow 시작/완료/오류
- 모델 후보 평가와 후보별 점수·제외 이유
- 선택 모델·route·정책·결정 요약
- Plan 단계, capability, Agent, Skill, Tool, 의존성, 선택 이유
- 단계 시작/완료/오류와 Artifact 경로
- Evidence/Schema Review 결과
- Reduce 결과와 전달 Context 요약

모델의 비공개 chain-of-thought는 수집·저장·노출하지 않는다. `secret`, `password`, `token`, `apiKey`, `authorization`, `cookie` 키는 이벤트 저장 전에 `[redacted]` 처리한다. 운영자가 필요한 것은 모델 내부 독백이 아니라 같은 입력에 대해 선택을 재현하고 장애 단계를 찾을 수 있는 구조화 근거다.

선택 미리보기는 실제 분석/시나리오 생성 Tool을 실행하거나 프로젝트 데이터를 변경하지 않고 Plan과 모델 결정만 생성한다.

## 11. 의도적으로 남긴 후속 Gate

- Orchestrator는 dependency-ready step을 계산하지만 현재 같은 ready group을 순차 실행한다. 실제 FE/BE 병렬 실행은 resource lock, rate limit, event ordering 계약을 추가한 뒤 활성화한다.
- 실행 checkpoint와 실패 단계부터 재개는 아직 구현하지 않았다. Plan v2와 Artifact reference를 기반으로 후속 Phase에서 도입한다.
- 모델 API key는 안전을 위해 메모리 전용이다. 운영 배포에서는 Vault/KMS 등 Secret Provider adapter가 필요하다.
- 현재 등록된 로컬 LLM profile health는 `unknown`이다. 관리 화면에서 `/v1/models` health를 실행해 실제 endpoint 상태를 확인해야 한다.
- Agent Trace는 운영 감사 로그이며 chain-of-thought 공개 기능으로 확장하지 않는다.
- Phase 14 포인터는 기존 배치 수용 Gate가 남아 있어 유지한다.
