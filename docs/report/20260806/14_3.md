## 1. 이번 단계에서 한 일

14_2에서 문서·프롬프트로만 세워둔 D-015(세션 선행조건 · 기대결과 대조 판정)를 **실제 실행경로**에 붙였다.
사용자가 지적한 세 가지를 순서대로 처리했다.

1. **지침을 실행경로에 붙임 (D-015)**
   - FE 분석기(`extract_flask_screens`)가 화면별 허용 method · 인증 가드 · 로그아웃 등 POST 전용 동작 form
     (접힌 메뉴면 여는 버튼 selector까지) · 인증 사용자에게만 보이는 세션 마커를 추출한다.
   - Interaction Graph에 `authContext`(로그인 경로 · 로그인 컨트롤 · 가드 라우트 · POST 전용 라우트 ·
     동작 트리거 · 세션 마커)를 담는다.
   - 시나리오 생성에 결정론 모듈 `session_precondition`을 붙였다. 인증 뒤 화면·로그아웃·잔액/거래내역 같은
     계약상 인증 업무는 `authRequired`·`sessionPolicy=login_then_reuse`가 되고
     **로그인 화면 열기 → 계정 ID 입력 → 비밀번호 입력 → 제출 → 세션 확인** 선행 단계가 앞에 붙는다.
     계정은 값이 아니라 참조(`environment.loginId` / `environment.loginSecret`)로만 둔다.
   - GET 직접 진입이 허용되지 않는 경로(`/logout`)는 URL 이동 단계를 제거하고
     **메뉴 열기 → 화면의 「Sign out」 클릭**으로 바꾼다. 로그아웃 뒤에는 세션 마커가 사라졌는지 확인하는
     `assert_absent` 단계를 둔다.
   - 실행기(`browser_execute`)는 연결 정보 계정으로 로그인하고 같은 세션에서 이어간다. 세션 확인이 막히면
     본 단계를 실행하지 않는다. 화면에 렌더된 거부 문구(405/401/403/Allowlist/서버 오류)를 관측하고,
     기준 항목별로 `expected_met|expected_not_met|undetermined`를 결정론으로 계산한다.
   - `run_service`는 이 판정으로 목록 상태를 정한다. **도달만으로는 「정상 관측」이 되지 않는다.**
   - 화면 경로가 분석에서 확정되지 않은(`missing_data`) 시나리오는 없는 주소를 열지 않고
     그 단계를 `missing_data`로 남긴다 → 판정은 `undetermined`.
   - 시나리오 상세에 `본 단계 전에 먼저 하는 일`(선행 로그인 단계·트리거 대체 사유)과
     `판정 기준 대조 목록`(기준 문장 ↔ 실제 관측)을 노출했다.

2. **분석 목록 = 하나의 그룹ID 한 행**
   화면(Frontend)·서버(Backend)를 각각 한 행으로 나눠 보여주던 목록을 그룹 1행으로 합쳤다.
   요약은 그룹 합계(화면·컴포넌트·엔드포인트), 선택·삭제도 그룹 단위다. FE/BE 구분은 행을 클릭한
   상세에서 전환한다.

3. **OTHERS 메뉴 공통 테이블 기능**
   실행 이력 · 증적 · HITL 승인 세 화면에 WORK 테이블과 같은 검색 + 전체선택 + 행 선택 + 선택 삭제 +
   행 삭제를 붙였다. 선택 상태와 삭제 호출은 공통 모듈(`lib/tableSelection.ts`)로 모았고,
   백엔드에 `POST /api/runs/bulk-delete`를 추가했다(증적 파일은 지우지 않고 목록에서만 제거).
