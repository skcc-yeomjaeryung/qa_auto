## 1. 문제와 수정 결과

기존 영상과 화면에서는 테스트 시나리오가 `확인 필요`인데 후속 실행 이력과 보고서가 성공처럼
보일 수 있었다. Run 조회와 Report 생성의 정규화 시점, Graph runtime 상태 투영, 화면별 상태
표현이 분리되어 있었기 때문이다.

이번 회차에서 동일 `runId`의 기술 상태와 `runDiagnosis`를 다음 화면에 관통시켰다.

```text
테스트 시나리오 목록·상세
  → 의존관계 Graph의 실패/확인 필요 노드
  → 실행 이력 AI 관측 요약·단계·증적
  → HITL 리포트 도넛·원인·조치·기술 검증·증적
```

- 직접 관측한 기대 불일치는 빨간색으로 표시한다.
- 데이터 변경 실행 승인 차단과 테스트 데이터 선행조건 부족은 주황색 `확인 필요`로 표시한다.
- 시나리오 상세는 최근 Run의 문제와 1차 조치, 같은 Run ID 링크를 모든 탭 위에 유지한다.
- Graph는 criterion/차단 step을 해당 노드에 매핑하고 테두리와 원인·조치 문구를 표시한다.
- Report Agent는 raw 저장 상태가 아니라 보수적으로 정규화한 Run에서 보고서를 만든다.

## 2. AI 관측 진단 품질

실패·확인 필요 결과는 문제, 원인 분류, 관측 증적, 담당자별 조치, 재검증 조건으로 구조화했다.
숫자 필드가 문자를 허용하는 경우에는 일반적인 “개발자 확인” 문구 대신 다음을 안내한다.

- `type=number`, `pattern`, `inputMode`, submit validation 확인
- 오류 UI 표시와 업무 API Network 요청 미전송을 함께 재검증
- 실제 DOM/계약 근거와 실패 criterion을 원인·조치에 연결

## 3. 근거 기반 예측 시나리오

Scenario DSL과 narration 지침에 사람이 놓치기 쉬운 위험을 능동적으로 탐색하도록 보강했다.

- 근거: HTML control 제약, Frontend 이벤트·바인딩, Backend API 계약
- 예측: 잘못된 타입, 필수값 공백, 최소/최대 경계, 중복 제출, 권한, 오래된 상태,
  API 성공 후 화면 미갱신
- 계약: `scenarioAugmentation.mode=grounded_risk_prediction`, hypothesis, evidenceBasis,
  confidence, humanReviewRequired, promotionRule
- 원칙: 예측은 결함 확정이 아니며 실제 실행 증적이 기대와 어긋날 때만 HITL 검토 대상으로 승격

실데이터에서 새 `DEPOSIT-E2E-007` 케이스가 한글 입력을 시도했고 브라우저 입력 제약이 요청 전에
정상 차단했다. 이는 결함을 꾸민 결과가 아니라 “인간이 놓칠 수 있는 케이스를 자동 생성하고 실제로
검증했다”는 성공 근거다.
