## 1. 왜 이 계약이 생겼는가 (관측된 결함)

```text
로그아웃 시나리오를 로그인 없이 /logout 경로만 열어 실행했다.
→ 서버가 요청을 거부했다 (Allowlist methods)
→ 로그아웃은 실제로 수행되지 않았다
→ 그런데 "Endpoint 에 접근했다"는 이유로 성공 플래그가 붙고 증적이 남았다.
```

두 가지가 동시에 잘못됐다.

1. **선행조건 누락** — 로그아웃은 로그인 세션 안에서만 성립한다.
2. **판정 기준 오류** — 도달·무예외·스크린샷 존재를 성공으로 취급했다.

같은 함정은 잔액·송금·거래내역·내 정보처럼 **인증 뒤에 있는 모든 화면**에 있다.
커버리지 숫자만 올라가고 아무것도 검증하지 않는 실행은 **결함**으로 다룬다.

## 2. 세션 선행조건 계약

### 2.1 `sessionPolicy` (시나리오 필드)

| 값 | 의미 | 실행기 동작 |
|---|---|---|
| `no_auth` | 인증 없이 성립 | 그대로 실행 |
| `login_then_reuse` | 선행 로그인 후 같은 세션 유지 | 로그인 step 수행 → 세션 확인 → 본 단계 |
| `reuse_existing_session` | 앞 시나리오 세션 승계 | 세션 없으면 로그인으로 승격 |
| `fresh_login_required` | 매번 새 로그인 | 세션 초기화 후 로그인 |

### 2.2 강제 규칙

1. `graphEvidence.authGuardedRoutes` 에 속하거나 로그아웃·잔액·송금·거래내역·내 정보를
   다루는 시나리오는 `authRequired: true` 이며 **로그인 선행 step을 포함**한다.
2. **로그아웃 시나리오는 예외 없이 선행 로그인을 포함한다.**
3. 로그인 값은 **연결 정보에 등록된 계정**만 쓴다.
   시나리오·프롬프트에는 값이 아니라 참조만 둔다 — `environment.loginId` / `environment.loginSecret`.
   비밀번호는 저장·출력·로그에 남기지 않는다 (마스킹 유지).
4. 로그인 직후 **세션이 생겼는지 화면 관측으로 확인**하는 step(`blocking: true`)을 둔다.
   실패하면 본 단계를 실행하지 않고 `session_missing` 으로 종료한다.
5. 후속 단계는 **같은 브라우저 세션**에서 이어간다. 쿠키·스토리지 조작으로 세션을 위조하지 않는다.
6. 로그인·로그아웃은 URL 직접 접근이 아니라 **화면의 입력·클릭(실제 사용자 이벤트)** 으로 수행한다.
7. 근거(로그인 경로·컨트롤 selector·계정 등록 여부)가 없으면 발명하지 않고
   `missing_data`(`graph:loginControls`, `connection.loginSecret` 등)로 남긴다.

### 2.3 배치 실행 순서

인증이 필요한 시나리오 묶음은 **로그인 시나리오 → 인증 필요 시나리오 → 로그아웃 시나리오** 순으로
정렬해 세션을 승계한다. 순서를 보장할 수 없으면 각 시나리오를 `login_then_reuse` 로 자립시킨다.

## 3. 기대 결과 판정 계약

### 3.1 필드

| 필드 | 값 | 뜻 |
|---|---|---|
| `verdict` | `expected_met` / `expected_not_met` / `undetermined` | 기대 결과 대조 결과 |
| `verdictReason` | 문장 | 그렇게 본 사유 (관측 사실 인용) |
| `criteriaResults[]` | `{id, expected, observed, result, reason, evidence[]}` | 항목별 판정 |
| `blockingIssues[]` | `{kind, detail, suggestedFix}` | 진행을 막은 원인 |
| `coverageNote` | 문장 | 이번 실행이 **검증하지 못한 범위** |
| `humanDecisionRequired` | 항상 `true` | 최종 판정은 담당자 |

`blockingIssues.kind` 는 `session_missing` · `method_not_allowed` · `element_missing` ·
`no_state_change` · `timeout` · `unknown` 만 쓴다.

### 3.2 강제 규칙

1. **도달 ≠ 성공.** 아래만 관측됐다면 `expected_met` 을 쓸 수 없다.
   화면·URL 을 열었다 / 요청이 갔다 / 스크린샷이 남았다 / 예외가 없었다.
2. 상태 변화(로그아웃·저장·전송·삭제)가 기대의 핵심이면 **변화 관측**이 있어야 한다.
   없으면 `not_met` 또는 `undetermined` + `no_state_change`.
3. `401` · `403` · `405` · `Allowlist methods` · 로그인 화면으로 되돌려짐 ·
   `sessionEstablished: false` 인데 인증이 필요함 → `expected_not_met` +
   `session_missing`/`method_not_allowed` + `suggestedFix` 에 **선행 로그인 추가**.
4. 기대 기준이 없으면 성공으로 올리지 않는다 → `undetermined` + `missing_data: ["expected_criteria"]`.
5. 항목 중 하나라도 `not_met` 이면 전체는 `expected_met` 이 될 수 없다.
6. 사유는 관측 사실(URL·응답 코드·요소 이름·단계)만 인용한다. "정상 동작함" 금지.
7. `coverageNote` 에 검증되지 않은 범위를 반드시 남긴다.
8. `verdict` 는 **기술 판정**이다. Pass/Fail·배포 확정은 HITL이다 (D-004 · D-009).

### 3.3 화면 표기

- Console은 `verdict` 와 `verdictReason` 을 **관측 표현**으로 보여준다
  (`정상 관측` · `실패 관측` · `판정 불가`). 「성공 확정」 표현을 쓰지 않는다.
- 실행 이력·증적에는 `verdict` · `verdictReason` · `coverageNote` 를 함께 남겨
  담당자가 왜 그렇게 관측됐는지 읽을 수 있게 한다.

## 4. 적용 체크리스트 (플랫폼 개발자)

- [ ] 시나리오 생성 산출물에 `authRequired` · `sessionPolicy` · `verdictCriteria[]` 가 있다
- [ ] 인증 필요 시나리오에 로그인 선행 step + 세션 확인 step(`blocking`)이 있다
- [ ] 로그아웃 시나리오에 선행 로그인이 포함된다
- [ ] 실행기가 연결 정보 계정으로 로그인하고 같은 세션을 유지한다
- [ ] 실행 결과에 `verdict` · `verdictReason` · `blockingIssues` · `coverageNote` 가 남는다
- [ ] 도달만으로 성공 상태가 되지 않는다 (회귀 테스트로 고정)
- [ ] 비밀번호·토큰이 저장·로그·응답에 남지 않는다
- [ ] Console·요약 문구에 Pass/Fail 확정 표현이 없다
