# 공통 구현 컨텍스트

## 1. 제품 정의

이 프로젝트는 **AI 기반 Code-to-E2E 관통 테스트 플랫폼 파일럿**이다.

플랫폼은 개발자의 Frontend와 Backend 저장소를 읽고 다음을 수행한다.

1. A 화면의 컴포넌트, 입력 속성, 이벤트, Route, API 호출을 정적 분석한다.
2. Backend Controller, DTO, Validation, Service 진입점, Response, 기존 테스트를 정적 분석한다.
3. Frontend API 호출과 Backend Endpoint를 연결한다.
4. `A 화면 → 컴포넌트 이벤트 → API Request → Backend 처리 → API Response → B 화면 이동 → UI 바인딩` 흐름을 Interaction Graph로 생성한다.
5. Graph를 실행 가능한 Scenario DSL **seed**로 변환한 뒤, SDD Plan의 LLM Skill로 한글 서술·바인딩 후보를 보강한다 (D-014).
6. 필수 입력과 제약을 추출하고 추천 테스트 데이터를 생성한다.
7. (선택) UI 기획 슬라이드·엑셀/CSV 테스트시트를 **보조 Evidence**로 받아 INPUT·설명·Assertion 후보를 보강한다.
8. **agent-browser MCP**로 실제 입력·클릭·Blur·Submit 이벤트를 발생시키고 DOM snapshot·스크린샷을 수집한다.
9. Frontend Network와 Backend Structured Log를 Correlation ID로 연결한다.
10. Backend Response와 B 화면 표시값을 검증한다.
11. Screenshot, DOM snapshot, Network, Backend Log, Assertion을 Evidence Package로 만든다.
12. 건별·배치 테스트를 제공한다.
13. 자동 검증 후 반드시 고객 HITL 승인 또는 반려를 받는다.

## 2. 1차 범위에서 제외

- 테스트 진척률 계산
- 개발자별 품질 점수
- 팀별 순위
- 미래 결함 예측
- 운영 Merge 자동 차단
- 운영 데이터 변경
- 모든 개발언어 지원
- DOM 또는 이미지 정보만으로 **확정** 시나리오 생성  
  (기획 PPT/이미지는 **보조 hint만** 허용. 코드 Graph·Contract와 join된 항목만 승격.  
  관측 재료 + Graph Evidence를 근거로 한 LLM **초안**은 D-014에서 허용)
- LLM의 근거 없는 기대값 확정
- SVN/GitLab/Bitbucket 정식 수집기 (1차는 GitHub URL · Local Path. 기타 VCS는 Local Path로 대체)

## 2.1 보조 입력원 (Optional Evidence)

코드 분석이 주 경로다. 아래는 **입력 피로도 완화용 보조**이며, 단독으로 Scenario/INPUT/기대값을 확정하지 않는다.

| 입력원 | 역할 | 등급 | 연결 Phase |
|---|---|---|---|
| Design Spec (PPT/이미지/PDF 슬라이드) | 서비스·거래 ID, 번호 주석, 조작·기대 동작 설명 | `hint` / `candidate` | 01 업로드 → 06·07 join → 08 의미 힌트 |
| Test Data Sheet (Excel/CSV) | 서비스·거래 ID 기준 요청·응답·업무상태 표본 | `catalog` (승인 전 `reviewRequired` 가능) | 01 업로드 → 08 입력원 |

### Design Spec 슬라이드 포맷 (권장)

```text
TOP    : 서비스/거래 아이디 및 타이틀
CENTER : 화면 캡처 + 번호 annotation
RIGHT  : CENTER 번호별 상세 설명(조작·노출·로직)
```

파싱 결과는 `DesignSpecArtifact`로 저장한다.  
코드 Evidence와 join 실패·DOM 부재 시 `missing_data`로 남기고 추정하지 않는다.

### Test Data Sheet (권장 컬럼)

```text
서비스/거래 아이디 | 요청 필드… | 응답/기대 필드… | 업무상태(선택)
```

서비스·거래 아이디를 키로 Fixture/Validation 다음에 참고한다.  
응답 기대값은 HITL 전 자동 최종 승인하지 않는다.

## 3. 대상 기술

### 분석 대상 Frontend
- TypeScript / JavaScript
- React
- Next.js App Router 및 Pages Router
- React Hook Form, Zod/Yup은 우선 지원
- fetch, Axios, React Query는 우선 지원
- (선택) 기존 Playwright Test — 대상 저장소 Evidence 추출용

### 분석 대상 Backend
- Java 17 이상 · **Spring Boot 3.x / Spring MVC 우선** (1차 sample 유지)
- Bean Validation · JUnit 5 · MockMvc · REST Assured
- 입력 workspace: Phase 01 — **GitHub URL** 또는 **동일 서버 절대경로** (SVN 등은 Local Path, D-007)
- ※ 대상 언어(Java/Spring) ≠ 분석 런타임 언어. 런타임은 아래 플랫폼 기술 참고 (D-010)

### 플랫폼 기술
- 루트 배치: **`frontend/`** (Console) · **`backend/`** (SDD Control Plane) — D-011 · D-012
- Control Plane (`backend/`): Python 3.12, FastAPI, Pydantic v2
- **SDD (D-012·D-016):** Workflow Hub + Skill Hub + 단일 `app/core` (`runtime`·`planning`·`execution`·`quality`) + LangGraph 공통 Plan 실행
- Web Console (`frontend/`): Next.js, React, TypeScript
- Analyzers: Skill Hub 경유 · `backend/workers/*` 외부 런타임 (FE=ts-morph, BE=Python Spring 분석, D-010 대상 유지)
- Browser Runner: **agent-browser MCP** (기본). Playwright MCP는 보완·레거시 경로이며 사용 전 사용자 문의
- Database: PostgreSQL
- Queue/Cache: Redis
- Evidence: Local filesystem을 기본으로 하되 S3-compatible adapter 인터페이스 제공 (screenshot + DOM snapshot + network)
- LLM: OpenAI-compatible local endpoint. **사실 확정 금지** — 요약·후보만. Hub 자산 발명 금지
- Common fallback parser: Tree-sitter. 단, 의미 분석의 주 도구로 사용하지 않는다.

## 6. 신뢰도 원칙

| 근거 | 기본 신뢰도 |
|---|---:|
| 명시적 코드 + 기존 테스트 Assertion 일치 | 0.95~1.00 |
| 정적 코드에서 직접 Route/API 확인 | 0.85~0.95 |
| Symbol을 일부 해결하지 못한 정적 추론 | 0.60~0.84 |
| Runtime 검증으로 보강 | 최대 1.00 |
| DOM/문구 기반 추론만 존재 | 최대 0.49 |
| Design Spec(Vision/OCR)만 존재 | 최대 0.49 (`hint`) |
| Excel/CSV Catalog(미승인) | 후보·`reviewRequired` (자동 확정 금지) |
| LLM 의미 추론만 존재 | 자동 확정 금지 |

신뢰도 0.70 미만의 Edge는 `unresolved`로 저장하고 건별 실행에서 확인하거나 Runtime 검증 대상으로 표시한다.  
Design Spec은 코드 Graph/Contract와 join되고 정적·Runtime Evidence가 붙을 때만 상위 신뢰도로 승격한다.

## 7. LLM 역할과 금지사항

### LLM이 수행 (D-014 에이전틱 시나리오 초안 포함)
- Graph의 업무 의미 요약
- 시나리오 **한글** 제목·단계 서술·서비스 라벨
- request/response/bindings **후보** (Graph·DSL seed·Contract Evidence 참조 시)
- 기존 테스트 통합
- 누락된 Assertion 후보 추천
- 입력 Semantic Type 후보 추천
- Design Spec annotation·엑셀 행을 코드 Evidence에 **매핑하는 후보** 제안
- 실패 로그 요약
- 고객 검증 질문 생성

### 시나리오 초안 경로 (D-014)
```text
Graph(결정론) → DSL seed(script) → narrate_and_bind(LLM Structured Output)
  → ScenarioSummary 저장 → agent-browser 실행 → Evidence(스크린샷·DOM) → HITL
```
- Graph 조성·DSL step skeleton(method/path/locator)은 script/rule
- LLM은 Hub에 등록된 Skill 안에서만 호출되며, Schema 검증 후 저장
- 근거 없는 필드는 `missing_data` (추정으로 채우지 않음)

### LLM이 수행하지 않음
- Commit/파일/라인 등 사실 조작
- 존재하지 않는 Endpoint 확정
- 근거 없는 기대값 확정
- Design Spec/엑셀만으로 Scenario DSL·INPUT·Pass 확정
- 테스트 성공 여부 판정 · Pass/Fail·배포 최종 확정
- HITL 승인 대행
- 원본 전체 저장소를 매 요청마다 Context에 주입
- Hub 미등록 Workflow/Skill/Tool 발명

LLM 출력은 반드시 JSON Schema 검증을 통과하고, 원본 Evidence ID를 참조해야 저장한다.

## 8. 실행 추적 헤더

모든 관통 테스트 요청에는 다음 헤더를 사용한다.

```http
X-Test-Run-ID: RUN-...
X-Scenario-ID: customer-search-detail-001
X-Scenario-Version: 1.0.0
X-Test-Case-ID: TC-...
X-Input-Profile-ID: PROFILE-...
```

Spring Filter/Interceptor는 이 값을 MDC와 Structured Log에 전달한다.

## 9. 보안·개인정보

- Secret, Password, Token, Cookie, Authorization Header는 저장하지 않는다.
- Request/Response 필드별 마스킹 정책을 제공한다.
- 실제 고객 개인정보 대신 합성·마스킹 테스트 데이터를 사용한다.
- Evidence 다운로드는 권한 검사를 거친다.
- 저장소 Token은 암호화하거나 Secret Store adapter로 관리한다.
- 외부 LLM API 호출을 기본 금지하고 로컬 endpoint만 허용한다.
- 테스트 대상은 Pilot/Sandbox 환경으로 제한한다.
- destructive action은 기본 차단한다.

## 10. 테스트와 품질 규칙

- 정적 분석기에는 Fixture Repository 기반 Golden Test를 작성한다.
- API와 Schema에는 Contract Test를 작성한다.
- agent-browser 실행에는 실패 시 Screenshot과 DOM snapshot을 자동 보존한다. (입력 직후·결과 화면 최소 2장)
- agent-browser / Playwright MCP 사용 전 사용자에게 문의한다. 무단 파괴적 크롤 금지.
- AI는 관측 요약만 제공하고 Pass/Fail·배포는 HITL이 한다. DOM에 없으면 `missing_data`.
- Python, Node, Java 모듈 모두 lint/test 명령을 제공한다.
- 외부 네트워크 없이 재현 가능한 로컬 테스트 경로를 제공한다.
- 테스트에서 임의 `sleep`을 사용하지 말고 snapshot/selector/network 조건 기반 대기를 사용한다.
- DOM에 직접 값을 주입하지 말고 agent-browser의 fill/click 등 실제 사용자 이벤트를 사용한다.
- Mock은 단위 테스트에는 허용되지만 통합 인수 Gate에서는 실제 Sample FE/BE를 사용한다.

## 11. UI 최소 화면

### 11.1 주 사용자 여정 (5단)

```text
1) 프로젝트 생성
2) 저장소(레포) 연결
3) 테스트시나리오 생성 진행
4) 테스트시나리오 목록 확인
5) 일괄 테스트 또는 개별 테스트 실행
```

여정·시나리오·스텝이 **진행 중 / 완료 / 오류·경고**일 때 Progress UI는  
Figma Progress Bar UI Kit 필수 ([`../02.아키텍처/04.진행상태UI.md`](../02.아키텍처/04.진행상태UI.md) · D-009).

### 11.2 화면 목록

1. 프로젝트/저장소 등록 (+ Type 2 파이프라인 Progress)
2. (선택) Design Spec · Excel/CSV 테스트시트 업로드
3. 분석 실행 및 결과 (시나리오생성 Progressing)
4. 시나리오 목록 (행별 Type 1 Progress)
5. 시나리오 상세 A→B Flow (Design Spec join 상태 표시)  
   — Flow UI는 Figma User Flow Kit 필수 ([Phase 05](../04.Phase실행바이블/05.InteractionGraph.md) · D-008)
6. 입력 추천값 검토 (Catalog/힌트 근거 포함)
7. 건별 테스트 실행 (Type 4 스텝 Progress)
8. 배치 테스트 실행 (Type 1/5 Progress)
9. Evidence Viewer
10. HITL 검증함
11. 감사 로그

## 12. 공통 구현 명령

각 Phase는 아래를 준수한다.

- 계획만 작성하지 말고 구현한다.
- 기존 코드를 우선 읽고 중복 구현하지 않는다.
- 변경 전후 테스트를 실행한다.
- 실패를 숨기지 않는다.
- 기능 플래그 또는 설정으로 단계적 활성화한다.
- 공개 API 변경 시 OpenAPI와 계약 Schema를 함께 갱신한다.
- 아키텍처 또는 규칙 변경 시 `AGENTS.md`를 갱신한다.
- 모든 Phase 결과를 `docs/06.완료보고/PHASE-XX.md`에 남긴다.
