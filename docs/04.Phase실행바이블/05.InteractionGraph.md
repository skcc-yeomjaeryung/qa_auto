# Phase 05 — A→B Frontend–Backend Interaction Graph 생성과 시각화

## 이 프롬프트의 역할

당신은 대형 SI 프로젝트용 AI Code-to-E2E 관통 테스트 플랫폼의 수석 개발자다.  
프로젝트 루트에서 먼저 다음 문서를 읽고 현재 코드 상태를 점검하라.

- `AGENTS.md`
- `README.md`
- `index.md`
- `00_common_context.md`
- `00_pilot_definition_of_done.md`
- 관련 JSON Schema와 이전 Phase 완료 보고서

계획 문서만 작성하지 말고, **실제 구현·테스트·문서화·완료 보고까지 한 번의 작업으로 수행**하라.  
모호한 부분은 기존 코드와 공통 문서를 근거로 합리적인 기본값을 채택하고, 구현을 중단하는 질문으로 돌리지 말라.

## Phase 목표


분석 결과와 API 매핑을 결합해 A 화면에서 B 화면까지의 관통 흐름, 필수 데이터, 분기, Evidence, Confidence를 언어 중립 Interaction Graph로 생성한다.


## 선행조건


- Phase 04 완료
- Interaction Graph JSON Schema 사용 가능


## 구현 범위


- Graph Builder
- Node/Edge 정규화
- 경로 탐색
- 분기와 unresolved edge
- A→B Flow 상세 API
- Web Console Flow 시각화 (**Figma User Flow Kit 필수 준수**)


## 상세 구현 요구사항


1. 최소 경로:
   `screen(A) → input → event → validation → frontend_api_call → backend_endpoint → request_dto → service → response_dto → route_transition → screen(B) → binding`
2. 각 Node/Edge는 Evidence, Confidence, verificationStatus를 가진다.
3. 동일 코드 요소의 중복 Node를 안정적 ID로 병합한다.
4. 정상/제한/오류 경로를 별도 branch로 표시한다.
5. 입력 필드에서 Backend Request, Response, B Binding까지 Data Lineage를 표현한다.
6. Graph는 특정 Frontend/Backend Commit 조합에 종속된다.
7. Graph 생성 시 Schema 검증을 수행한다.
8. Cycle과 동적 dispatch는 시각화하되 무한 경로 탐색을 막는다.
9. Graph 상세에서 파일/라인 Evidence를 열 수 있다.
10. 시각화는 A/B 화면을 강조하고 API/Backend 구간을 구분한다.
11. Graph 생성 결과가 LLM 호출 없이도 설명 가능한 기본 라벨을 제공한다.
12. **Flow UI는 아래 「Figma MCP 필수 UI/UX」를 따르지 않으면 Gate 실패로 본다.**

### Agent 구현 절차 (필수)

```text
1) Figma MCP get_metadata(fileKey, nodeId=0:1) 로 kit 구조 확인
2) get_design_context / get_screenshot(nodeId=1:319) 로 Example 레이아웃·연결 패턴 확보
3) Screens / Arrows / Conditions / Comments / Nodes 심볼을 프로젝트 UI로 매핑
4) Interaction Graph Node/Edge 데이터를 위 비주얼 언어로 바인딩
5) 스크린샷·design context와 시각적 대조 후 완료 보고에 Figma node 인용
```

- 사용 전 사용자에게 Figma MCP 사용 여부를 확인한다 (공통 MCP 규칙).
- `get_design_context` 출력은 **REFERENCE**다. Next.js·기존 토큰·컴포넌트에 맞게 이식한다.
- Tailwind가 프로젝트에 없으면 임의 설치하지 말고 기존 스타일 체계로 변환한다.

### Kit → Graph 매핑

| Figma 영역 (node) | 비주얼 역할 | Interaction Graph 매핑 |
|---|---|---|
| Screens (`1:289`) — Base / Form / Landing / Portal / Organization / Email / Success Modal / Empty | 화면 카드(브라우저 프레임·타이틀) | `screen`, `component` (A/B 강조) |
| Arrows / Solid · Dotted (`1:88`, `1:230`) — Straight / Corner / Curved / Hook / Bypass | 직교·곡선 커넥터 | Edge: `triggers`, `calls`, `navigates_to`, `binds_to` |
| Conditions (`1:531`) — Base / Paths | 분기·조건 라벨 pill | `branches_to`, 정상·제한·오류 path |
| Comments (`1:499`) — Default / Warning | 화면 하단 주석·경고 | Evidence 요약, unresolved / `missing_data` |
| Nodes (`7:511`) — Default / State Positive·Negative | 연결점·상태 점 | Confidence / verificationStatus 배지 |

### Example(`1:319`)에서 반드시 재현할 UX

1. **화면 노드**: 상단 타이틀 + 브라우저형 카드(헤더 바·라운드 프레임). 내용 영역은 wireframe 플레이스홀더로 단순화해도 되나 카드 언어는 kit과 동일.
2. **엣지**: 직교/코너/곡선 화살표. 라인 위에 **회색 pill 라벨**(이벤트·조건·API 요약).
3. **분기**: Paths/Conditions로 다중 출구(정상·제한·오류)를 한 캔버스에 표현.
4. **주석**: Comment/Warning 블록으로 Evidence·주의 문구를 노드 아래에 배치.
5. **탐색**: 큰 Graph에서도 핵심 A→B 경로를 먼저 보이게 하고, 세부 Node는 확장한다 (기존 UI 요구와 동일).
6. **도메인 색 구분**: FE 화면 카드 / API·Backend 구간을 시각적으로 구분하되, kit의 Accent(`#3300FF` 계열)와 Arrow(`#1A1A1A`) 언어를 우선한다. 프로젝트 토큰이 있으면 kit 비율에 맞게 매핑.

### 금지

- Figma를 열지 않고 Flow UI를 자체 발명
- 테이블·아코디언만으로 A→B Flow를 “대체”
- Example과 무관한 일반 flowchart 라이브러리 기본 테마 그대로 사용 (라이브러리는 엔진으로만 쓰고 **스킨은 kit 준수**)
- Pass/Fail 색으로 고객 승인을 단정 표현 (State Positive/Negative는 기술 상태·Confidence용)

## UI 요구사항


시나리오 상세의 전 단계로 다음을 제공한다.  
**레이아웃·컴포넌트 언어는 위 Figma User Flow Kit / Example을 따른다.**

- A 화면 카드: Route, Screenshot placeholder, 입력 (Screens 계열)
- 이벤트 · API Request · Backend · API Response (커넥터 + pill 라벨)
- B 화면 카드: Route, 바인딩 필드 (Screens 계열)
- branch / Paths (Conditions)
- Evidence panel · Comments/Warning
- Confidence 및 unresolved badge (Nodes State)

큰 Graph에서도 사용자가 핵심 경로를 먼저 보고 세부 Node를 확장하도록 한다.  
완료 보고에 **참조한 Figma fileKey·nodeId**와 MCP로 대조한 사실을 기록한다.
